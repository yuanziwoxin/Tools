# 外框与概要改造方案 · 思维导图工具

> **状态**：**外框 P1 已交付（v41 · 2026-11-01）**、**概要 P2 已交付（v42 · 2026-11-02）**、**分组框 N9 已交付（v43 · 2026-11-02）**，P1.5 的 XMind 部分也已补齐 —— 见 [CHANGELOG](../CHANGELOG.zh-CN.md)
> **对象**：`mind_map.html`（v43 / 11352 行 / 652251 字节，单文件零依赖，12 种导出）
> **后续追加**：分组框（N9）是 P1/P2 之后用户提出的一条新需求 —— 「框住选中的这几个节点」。
> 它不属于原方案的外框/概要二分，设计见第 10 节；要点是**独立对象 + 背景层、不参与布局**。
> **原型**：[`外框原型.html`](外框原型.html) —— 外框的可点版本（仅屏幕渲染，导出未接）；正式实现已进主文件，原型保留作对照
> **目标**：补上同类工具里两个高频的"结构化表达"能力 —— **外框（Boundary）** 与 **概要（Summary）**
> **原则**：零依赖底线不变；两套布局共用同一套坐标语义不变（`x`=左沿、`y`=垂直中心）；沿用项目四步验收铁律

## 0. 结论先行

| | 外框（Boundary） | 概要（Summary） |
| --- | --- | --- |
| 本质 | 挂在节点上的装饰，随子树一起走 | 非树关系：一段**区间** + 一个附属主题 |
| 难度 | ★★☆☆☆ 中低 | ★★★★☆ 高 |
| 产品代码 | **350–420 行** | **600–700 行** |
| 触及模块 | 9 个 | 16 个 |
| 数据结构 | 节点 +1 字段，无身份问题 | +字段 +**区间身份** +顺序约束 |
| 导出要改 | 5 种（PNG / SVG / PPTX / XMind / JSON） | 8 种 |
| 回归风险 | 低 | 中高（布局与大纲） |
| 工期 | 2–3 天 | 4–6 天 |

三句话概括：

1. **外框是"加法"**——在现有模型上加一层装饰，最坏情况是画得不好看，改两行 CSS 就能退。
2. **概要是"改模型"**——它要在纯树里塞进一段区间关系，而 `colX` 按 depth 算列宽的前提会直接被打破。
3. 所以建议**先外框、后概要**，且概要第一版把范围锁在"同一父节点下的连续区间"。

## 1. 架构前提：为什么两者不是一个量级

现有引擎的每一层都建立在一个前提上：**数据是一棵纯树，每个节点只属于一个 depth，同一个 depth 的所有节点对齐在同一列**。

| 层次 | 依赖"纯树"的具体实现 | 概要带来的冲突 |
| --- | --- | --- |
| 布局 | `colX[depth]` 全局按层算列起点（`render()` 里 `colW[]` 汇总，第 5437 行附近） | 概要主题不属于任何一层，落在"半级"上 |
| 布局 | `layout()` / `layoutOrg()` 只遍历 `children`（3767 / 3820） | 区间是"兄弟之间"的关系，`children` 表达不了 |
| 渲染 | `flat` 由 `walk` 递归 `children` 生成（5392） | 概要主题要么进 `children`，要么得再写一套遍历 |
| 连线 | `drawEdges()` 一律"父 → 子"，端点由 `edgeGeom()` 给（5652 / 3847） | 概要不是父子连线，是**括线** |
| 存档 | `serialize()` 只认白名单字段（3366） | 新字段不写进去就会被静默丢弃 |
| 撤销 | 整棵树的 JSON 快照（`snapshot()`） | 区间索引得跟着结构改动一起维护 |

外框只碰到其中 **3 条**（布局预留、渲染加层、存档加字段），概要碰到 **6 条**。

## 2. 外框方案

### 2.1 交互契约

| 操作 | 入口 | 结果 |
| --- | --- | --- |
| 添加外框 | 右键 → 「添加外框」 | 以该节点为根、包住它和全部可见后代 |
| 改标题 | 双击框上标题（行内编辑） | 标题为空时不显示字样，只留边框 |
| 改颜色 | 右键 → 颜色色板（复用 `NODE_COLORS`） | 边框与标题同色，底色取同色淡铺（v41 是 8%；v44 定稿 20%，见 11.7） |
| 删除 | 右键 → 「删除外框」 | 只删框，不删节点 |
| 复制 / 克隆 / 粘贴 | 无感 | 外框随子树一起复制（`serialize` 走同一条路） |

**刻意不做**（范围边界）：不做多选批量加框、不做嵌套限深、不做"框上右键菜单"。

### 2.2 数据结构

字段挂在节点上——**删节点，框自然没了**，不需要任何引用清理：

```js
{ text: '分支 A', bd: { t: '可选标题', c: '#7F77DD' }, children: [ … ] }
```

`build()`（3352）收下、`serialize()`（3366）写出，各 3 行。老存档没有 `bd`，天然兼容；
`localStorage` 键 `mindmap-studio-v1` **一个字不动**。

> **已知代价**：新版存的文件用旧版打开，`build()` 只认白名单字段 → 再存一次外框就没了。
> 同款风险在 `link` / `mark` 引入时也存在过，属可接受的数据前向不兼容。

### 2.3 布局：只预留内边距，不动列模型

外框要"包住"子树，就得让上下相邻的分支让出位置，否则两个框会撞在一起。

| 位置 | 改法 | 行数 |
| --- | --- | --- |
| `layout()`（3767） | 该节点有 `bd` 时，子树块上下各加 `BD_PAD`：进入时 `cursor = yTop + pad`，返回 `span + pad * 2`；叶子返回 `node.h + pad * 2` | 12 |
| `layout()` 兄弟间距 | 相邻两支**只要有一支带框**，中间再补一个 `BD_PAD`——否则两个框只隔 `GAP_Y = 12`，看着贴在一起（原型实测：补之前 12px，补之后 26px） | 2 |
| `orgMeasure()`（3808） | 有 `bd` 时 `total += BD_PAD * 2`，让兄弟子树在横向上让出位置 | 4 |
| `shiftSubtree()`（3763） | 无需改（只做整体平移） | 0 |
| `colW[]` 与 `colX[]` | **无需改**：`GAP_X=64` 远大于 `BD_PAD=14`，框的右沿伸进列间隙也不会压到下一列 | 0 |

取 `BD_PAD = 14`：两个相邻的带框分支之间实际留白 ≈ **26px**（`GAP_Y 12 + BD_PAD 14`），原型里量过，刚好分得开又不散。

> **v46 修正**：26px 这个数只回答了「两个框自己别贴」，没回答「框沿离**别人的卡片**」。用户第二句反馈就是后者。
> 现在拆成两个量：`BD_PAD = 20`（框沿离自己的节点）、`FRAME_CLEAR = 20`（框沿离隔壁的卡片或另一个框沿），
> 兄弟让位按一条式子算（外框的留白已含在 `layout()` 返回高度里，不再额外让；分组框只补超出那截；同组不让）。
> 真 Chrome 1:1 量到：框沿离节点 20、外框底边离下一张卡片 56、外框与分组框之间 20。

纵向布局（组织结构图）**只在横向加 `BD_PAD`**，纵向靠原有的 `ORG_GAP_Y = 44` 就够——`44 > 2 × 14`，框边落在行间的空白里，不需要改 `orgRowY()`。这是外框能低成本落地的关键：**它只需要"空间"，不需要"新的一列"**。

> **v46 修正**：`BD_PAD` 提到 20 之后这条不等式不成立了 —— `44 < 2 × 20 + 框线`，两层留白吃掉 40、只剩 4px 给框线自己。
> 所以 `ORG_GAP_Y` 一起从 44 提到 **52**。仍然不用改 `orgRowY()` 的结构，只是把常数对齐到新的留白。

### 2.4 渲染：新增一层 `#frames`

```
#viewport
  ├─ #frames   ← 新增，绝对定位、零尺寸、子元素按世界坐标摆
  ├─ #edges    ← 现有连线（pointer-events:none）
  └─ #nodes    ← 现有节点
```

放在 `#edges` 之前，于是**框在所有线之下、所有节点之下**，不会有色块压住文字。

`renderFrames()` 在 `render()` 里节点定位完成、`drawEdges()` 之后调用（同一趟 `try`，`rebuildingDOM` 闸门内）。它按每个带框节点递归求**可见后代**的包围盒（`collapsed` / `__cut` / `__fcut` 一律不进），再外扩 `BD_PAD` 画一个圆角虚线框 + 左上角标题。折叠或"只显示到第 N 层"时，框自动收窄到可见部分——不用特判，这是包围盒算法的自然结果。

## 3. 概要方案

### 3.1 三种建模对比

| 方案 | 覆盖范围 | 代码量 | 难度 | 说明 |
| --- | --- | --- | --- | --- |
| A | 某个父节点的**全部**子节点 | ~380 行 | ★★★ | 区间退化成"全体"，不需要身份标识；但用户想框住"三个里的前两个"就做不到 |
| **B** | 同一父下的**连续区间** | **~600 行** | ★★★★ | 与 XMind 行为一致，推荐 |
| C | 任意多选、跨父、不连续 | 900+ 行 | ★★★★★ | 需要节点 id + 多段括线，收益不成比例 |

### 3.2 推荐建模：概要主题 = 父节点的"特殊子节点"

不另建 `sums[]` 数组，而是让概要主题直接进 `children`，靠一个标记说明它覆盖谁：

```js
{ text: '中心主题', children: [
    { text: '分支 A' },
    { text: '分支 B' },
    { text: '分支 C' },
    { text: 'A 与 B 的共同点', sum: { a: 0, b: 1 } }   // 覆盖第 0、1 个子节点
] }
```

**为什么这样最省**：`makeEl()` / 选中 / 双击编辑 / 加子节点 / 上色 / 撤销 / 复制粘贴 / 大纲 / 统计 / 导出遍历，**全部白拿**，一行不用写。若另起数组，这 9 条路径每一条都要单独处理，代码量至少翻 40%。

代价是要在 4 处做"特殊处理"：

1. `layout()` 里它不参与正常折行，单独摆在区间中点右侧（纵向布局里是下方）。
2. `drawEdges()` 跳过它与父的连线，改由括线画出来。
3. `children` 顺序上它必须固定在末尾——`addSibling()` / `moveNode()` 遇到它要跳过。
4. `doneStat()` 不把它算进分支完成度。

### 3.3 区间身份：索引 + 每次结构改动后 clamp

工具现在**节点没有 id**（`build()` 3352 只带 text/note/color/mark/done/link）。选 B 就要接受索引区间：

- 规则一：在区间**中间**插入同级 → 区间自动扩张（`b++`）。
- 规则二：删除区间内的节点 → 区间收缩；删到空 → 概要一并删除。
- 规则三：任何结构改动后跑一次 `clampSums(parent)`，把 `a/b` 收进合法范围，越界则丢弃。

结构改动点一共 **15 处**：`addChild` / `addSibling` / `deleteNode` / `deleteChildren` / `deleteSelection` / `pasteSubtree` / `pasteTextAsSubtree` / `cloneNode` / `attachNode`（拖拽改父）/ `outlineMove` / `bulkSplit` / `bulkMerge` / `pruneExcluded` / `parseDoc` / `commitEdit`。

> 想彻底消灭漂移就给每个节点加 `id`（序列化体积 +8%，撤销快照跟着变大），不建议在 v1 做。

### 3.4 布局：概要要求"半级列"，这是主要成本

现有模型是"一列 = 一层"。概要主题和括线落在两级之间，`colX[depth]` 表达不了。方案是在 `layoutTree()` 之后加一趟后处理：

1. 先按原有逻辑排完所有真实节点。
2. 对每个概要：取它覆盖的区间在屏幕上的垂直中点（纵向布局取横向中点），括线放在区间右边界 + 8px，概要主题再往右 → 得到它需要的右沿。
3. 把它超出的宽度记进该列的右界，把 `depth + 1` 之后的列**整体右移**。
4. 两套布局各写一份（横向 / 纵向），约 120–140 行。

副作用要接受：**右移是全局的**，其他分支在同一层也会跟着变宽（多出一点空白）。局部重排（只推当前子树）需要改写 `colX` 的语义，投入产出不划算。

### 3.5 渲染：括线与连线分开画

括线走与 `drawEdges()` 同级的 `drawSums()`：一条竖线 + 两端的短横，再从竖线中点连一条短线到概要主题左沿。概要主题本身是普通节点元素，由 `makeEl()` 生成，只是位置由后处理给定。

### 3.6 导出的一个两难

概要主题既是"内容"（有文字、可能有子节点），又是"结构标注"。三选一：

| 口径 | 表现 | 代价 |
| --- | --- | --- |
| 当子节点导（推荐） | MD/Word/Excel 里多一行，缩进与兄弟同层 | 零成本，因为它就在 `children` 里 |
| 当标注导 | 大纲里单独一段"概要：…" | 要改 5 处导出 |
| 不导 | 文本导出丢信息 | 用户会问"我的概要呢" |

视觉类导出（PNG / SVG / PPT / XMind）无论如何都要画。

## 5. 风险与回退

| # | 风险 | 影响 | 处置 |
| --- | --- | --- | --- |
| 1 | 旧版打开新版文件 → 字段静默丢失 | 数据"看起来消失了" | 文档里写明；或在 JSON 加 `v` 并在导入时提示 |
| 2 | `colX` 全局右移，其他分支一起变宽 | 观感变松 | 提前告知，可接受；不做局部重排 |
| 3 | 布局类改动 jsdom 量不到 | 假绿 | 全部尺寸断言进真 Chrome（已有先例：`QA` 误判截断） |
| 4 | 撤销快照变大 | 80 步上限吃紧 | 外框每节点约 20 字节，可忽略；概要同理 |
| 5 | 只导出选中这一支时区间跨出范围 | 括线指向屏外 | 区间裁剪到范围内，越界则整条丢弃 |
| 6 | 无障碍：外框 / 概要在 ARIA 里没有对应角色 | 屏幕阅读器完全感知不到 | 框加 `aria-label`，大纲里显式一行 |
| 7 | 新增浮层 → 现有 3 处"14 张浮层"断言 | 连带改测试 | **两者都用行内编辑，不新建浮层**，绕开这条 |
| 8 | i18n 词表 905 条要同步扩 | 英文界面残留中文 | 每批新增文案同步进 `_i18n_en_*.json` |

回退方式：外框只加了一层 DOM 与一个字段，删掉 `renderFrames()` 调用即恢复原样（旧数据里的 `bd` 只会被忽略）；概要改动面大，建议独立分支。

## 10. 追加：分组框（N9 · v43 已交付）

用户的一句话需求：**「现在看着不能为多个节点加外框」**。

这里其实有两种语义，成本差一个量级 —— 必须先分清楚：

| 语义 | 做法 | 成本 |
| --- | --- | --- |
| A. 批量加框 | 选中 3 个节点 → 各自得到一个框（3 个框） | 把 `bdAdd/bdDel/bdSetColor` 改成遍历 `selectionRoots()`，改动很小 |
| B. 一个框包住这一组 | 选中 3 个节点 → 一个框把它们圈起来（XMind 的 boundary 语义） | 新对象 + 新几何 + 新导出，成本高一个量级 |

**用户拍板选 B**（`AskUserQuestion` 里明确选的是「一个框包住这一组」）。

### 10.1 三条设计取舍

1. **存法：组定义在根、成员挂 id。** `root.groups:[{id,t,c}]` + 节点 `gb:<id>`。
   不用概要那套索引区间 —— 区间要求「同父且连续」，而分组框最常用的场景恰恰是**跨分支**。
   副产品：复制 / 粘贴子树时 `gb` 指向的组不存在，`normGroups()` 一步收掉，**「粘出来的不带组」零代码**。
2. **不参与布局。** 它是背景层，画在连线与节点之下，`#frames` 本来就在 `#edges` 之前，DOM 顺序再往前塞一层就行。
   让位要重排整棵树，跨分支的组又没法局部让位；线在背后被节点盖住，视觉上已经足够「框住」。
   **这是本轮最重要的一条**：反证 ① 就是给 `layout()` 加一行让位代码，坐标断言立刻变红。
   > **v44 修正**：这一条在 10.2 的实测里被证伪了 —— 留白 22 > 兄弟间距 12，框的上沿必然探进上一支的卡片，
   > 那一段虚线就被节点盖住（用户报的第一个问题）。所以现在**纵向**会补一道 `GB_GAP` 让位，
   > **横向**仍然一位不动。详见第 11 节。
3. **收口只在一处。** 与 `clampTree` 并列，`render()` 开头一次 `normGroups(root)`：
   丢无效组定义、丢孤儿 `gb`、成员不足 2 人的组自动解散。结构怎么变都不怕漏调。

### 10.2 三个「框」的分工（写进 USAGE 3.12 的那张表）

| 形态 | 框住谁 | 谁来定范围 |
| --- | --- | --- |
| 外框 | 一条分支 + 它的可见后代 | 那个节点自己 |
| 概要 | 同一父节点下连续几个兄弟 | 选中区间（并生成概要主题） |
| 分组框 | 选中的任意几个节点 | 多选（可跨分支、可不连续） |

### 10.3 这轮踩到的两个真问题（都是真 Chrome 才暴露的）

- **标题位置**：最初放**左下角外侧**，结果正好压在下一个兄弟的头顶 —— 框在节点之下，标题就点不到了
  > **v44 补充**：两处框标题后来被统一成**一颗组件**（同字号 / 行高 / 内边距 / 圆角 / 边框 / 底色来源），
  > 只有「贴哪儿」不同 —— 外框骑框线、分组框在框内顶部，如上所述，是各自的遮挡条件逼出来的，不是两套样式。
  （`elementFromPoint` 返回的是 `node branch`，不是 `gbft`）。改成**上边居中**：
  单节点外框的标题在左上、不打架；上探 11px < 兄弟间距 12px，也不出界。
- **PNG 淡底色判不出来**：4.5% 的淡色叠在白底上只剩 ~245，测试用 `< 245` 当阈值，把「有底色」判成白。
  改成读具体像素值（235–253 之间），因为「数非白像素」分不出淡色与实色。

## 11. 追加：联系（N11 · v44 已交付）

用户原话是「增加节点、分组框、外框和概要之间的联系功能」。`AskUserQuestion` 里给了两种理解，
用户选的是 **「关联线（可写标签）」** —— 任选两个对象画一条带说明的线，等价 XMind 的「联系」（relationship）。

于是这一节要解决的不是「怎么画」，而是**两个没有 id 的东西怎么被一条线指着**。

### 11.1 端点的四种类型与一个代价

| 端点 | 落在哪 | 怎么判它还在 |
| --- | --- | --- |
| `node` | 节点本身 | `uidIndex()` 里查得到 |
| `bd` | 那个节点的外框 | 查得到且 `n.bd` 还在 |
| `sum` | 那个概要主题 | 查得到且 `n.sum` 还在 |
| `grp` | 分组框（它**不是**节点） | `root.groups` 里有这个 id |

前三类都落到「某个节点」上，而本工具的节点**从来没有 id**（概要的区间、分组框的成员标记都是这个前提）。
所以这是全文第一次给节点发 id：`n.uid`。

**关键取舍：只在被当成端点时才发，不给全树发。** 全树发 id 会改变 `serialize()` 的体积、
也会让 40 多套既有断言里的「节点对象形状」多出一个字段。按需发则完全不影响存量 —— 代价是**复制 / 粘贴必须剥掉**：
两份快照顶着同一个 `uid`，联系就会指到两个节点上。`stripUid()` 在 `pasteSubtree` 与 `cloneNode` 两处调用，
反证里拆掉其中一处，`粘贴后副本的 uid 被剥掉` 立刻变红。

### 11.2 收口：一处就够

`render()` 开头一次 `normLinks(root)`：

- 端点失效（节点删了 / 外框去掉 / 概要没了 / 组解散了）→ 丢掉这条联系；
- 自己连自己 → 丢掉；
- 重复 id → 只留第一条；
- 一条都不剩 → 连 `links` 字段一起删掉（不留空数组污染 JSON）。

好处和 `normGroups` / `clampTree` 完全一样：**结构怎么变都不用各处记得清理**。

### 11.3 几何：为什么是曲线而不是直线

直线连接两个矩形会出现两种丑：平行相邻时贴在一起分不清谁是谁；跨列时从一堆卡片中间穿过去。

所以：先 `rectEdgePt()` 求「矩形中心朝对方射出去的边交点」，再用三次贝塞尔，两端控制点各留一段直出、
并沿**法线**鼓 `k = clamp(16, d*0.16, 44)`；第 `i` 条按 `i%2` 交替正负，避免多条联系叠成一条。

### 11.4 图层：一条承诺，一个副作用

```
#frames → #edges → #rlinks → #nodes → #rlabels
```

- 曲线在节点**之下**：永远不压字。跨过卡片时从卡片背后过去，视觉上就是「一条线绕到后面」。
- 标签在节点**之上**：不然点不到（标签要双击改说明、右侧 `×` 要能点）。

副作用很实在：**中点经常正好落在「中间那一支」的卡片上**，标签就盖住了别人的字（截图里一眼看得见）。
所以加了 `pickLabelPt()`：中点压到卡片就沿曲线向两侧按 5% 步长找第一个空位（`PAD=13` ≈ 药丸半高 + 余量），
找不到就老实回中点。屏幕 / PNG / SVG 三处共用同一个落点 `o.la`。

> 这一条是**先有截图、后有断言**的典型：jsdom 里标签位置永远「对」，因为它不跑 transform、也不管遮挡。
> 教训：视觉功能的验收要**先看图**，再写断言把看到的问题钉住。

### 11.5 导出：四种输出，一个几何源

| 输出 | 联系 |
| --- | --- |
| PNG | `paintLinkPaths()`，标签画成白底药丸（导出底色是白，所以药丸也写白） |
| SVG | `<g data-rlinks="1">`（曲线 + 箭头）与 `<g data-rlklabels="1">`（药丸 + 文字），排在节点组之前 |
| JSON | `links` + 端点节点的 `uid` |
| XMind | sheet 上的原生 `relationships:[{id, end1Id, end2Id, title}]` |

XMind 有一个绕不开的缺口：**分组框不是主题**，没有 topic 可指。做法是落点取它的**第一个成员** ——
宁可在 XMind 里指到组里的一个节点，也不要整条联系凭空消失。这条在反证里专门盯着（拆掉落点分支就变红）。

文本类（MD / Word / Excel / OPML / PPT 大纲）**刻意不带**：线性大纲里没有「两个对象之间」这个位置，
硬塞一行反而会让人以为是子节点。

### 11.6 顺带修的两个真问题

1. **面板没样式**：`.lk-tip` 只作用在 `#link`，`.rlk-row` 压根不存在。联系面板会挤成一团。
   —— 新浮层务必回头看一眼「样式是不是只挂在老 id 上」。
2. **测试验的是自己**：「粘贴剥 uid」最初在测试里手写了 `stripUid(c)`，产品那行删掉也不会红。
   改成走真实入口 `pasteSubtree`。**反证不红的第一反应应该是「测试有洞」，不是「产品没问题」。**

### 11.7 v44 第二轮：把「显眼」做成可量的事

用户在第一轮上线前又提了三条，全是外观：**框还是太浅**、**两处框标题一个大一个小**、**概要节点跟普通节点没区别**。
这类问题的共同点是：改回原样功能一条不少，测试照样全绿。所以每条都要有一个**可量的下界**。

**框的显眼 = 三个量相乘**：线够深、底够实、**线够粗**。第一轮只做了前两个（14% / 7.5%），被一句「还是太浅」打回；
32%、38% 两轮也没过，最后落在 **45% 压暗 + 20% / 24% 同色淡底 + 2.4 / 2.6px 线宽 + 6/4 更密的虚线**。
第三个量一开始没有断言 —— 这意味着把 2.6px 悄悄改回 1px，界面立刻糊成浅虚线而测试全绿。
现在有一条「框的线比节点卡片的描边（1.4px）粗」，参照物就是卡片：框是**一片区域**的边界，必须比一张卡片重。

**标题统一**顺手带出一个几何问题：分组框标题那条留白带是 `GB_PAD=22`，而标题 21px + 新边框 2.6px = 23.6px，
装不下。于是留白提到 **26**，`GB_GAP` 用公式（留白 + 2 − 兄弟间距）自动跟着长 —— 这个公式当初写成推导而不是常数，
这一轮省下了「改一个数、找四处硬编码」的麻烦。测试里那条上界也从写死的 `+23` 改成读 `GB_PAD`。

> **v46 修正**：`GB_PAD` 再提到 **36**（= `BD_PAD 20 + 16`，标题带 + 边框仍装得下），同时 **`GB_GAP` 这个常量被删掉**。
> 公式化的红利吃完了：现在让多少由 sibling 让位那一条式子现算，`GB_GAP` 那种"留白 + 2 − 间距"的反推会让
> 两个量互相牵着走（改 `FRAME_CLEAR` 要重算 `GB_GAP`）。删掉之后只有一处定义，`boundary.js` 里也换成读常量。

**概要的「不一样」不能靠换颜色**：跨分支比颜色是假对照（分支色本来就不同，怎么改都「不同」，永远绿）。
做法是**同一个节点把 `sum` 标记摘掉再比** —— 这才是同一分支色下的对照组。四条差异都是「更重一档」：
药丸形（整圈圆角、去掉左侧竖色条）、底色更重（浅色 0.70、深色 0.55）、描边用分支色实色、文字 700。
深色主题不能照抄浅色那档，否则正好等于深色主题里普通浅层节点的底色。

> 验收：jsdom 三套新增 / 改写 9 条（含「框线比卡片粗」「两处标题字号逐项相等」「同色对照」）；
> 反证 `_falsify_v44b.py` **11 颗螺丝**（① 压暗退回 5% ② 底色退回 1% ②b/②c 线宽退回 1px
> ③ 标题字号改小 ④–⑨ 概要的形状 / 着色 / 圆角 / 深色档），每颗都咬得住；
> 全量回归与五组真 Chrome 探针全绿。
